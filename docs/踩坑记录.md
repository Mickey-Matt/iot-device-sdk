# 踩坑记录

## 1. 程序启动即退出，无输出

退出码 `-1073741511`。

转十六进制是 `0xC0000139`，`STATUS_ENTRYPOINT_NOT_FOUND`。用 objdump 查依赖：

```bash
objdump -p libmosquitto.dll | grep "DLL Name"
```

`libmosquitto.dll` 还依赖 `libcrypto-3-x64.dll`、`libssl-3-x64.dll`、`libwinpthread-1.dll`，
exe 自己还需要 `libstdc++-6.dll`、`libgcc_s_seh-1.dll`。

我最初只复制了 `libmosquitto.dll` 一个。依赖是传递的，只复制直接依赖不够。

改法：`CMakeLists.txt` 里 POST_BUILD 批量复制 6 个 DLL，另外加 `-static-libgcc -static-libstdc++` 去掉两个 GCC 运行库依赖。

## 2. 断线后不重连

broker 挂掉后不重连，而且每 20ms 往日志刷一条：

```
[ERROR] 数据源错误：MQTT 连接异常：The client is not currently connected.
```

原因是我最初用手动网络循环：

```cpp
const int rc = mosquitto_loop(mosq_, 0, 1);   // 主循环里每 20ms 调一次
```

`mosquitto_loop()` 不处理重连。查 `mosquitto.h` 第 1207-1216 行：

> The two recommended approaches are to use either **mosquitto_loop_forever** or **mosquitto_loop_start**.
> Use this function [loop_start] when you have other tasks you need to run at the same time as the MQTT client.

自动重连是 `loop_forever` / `loop_start` 提供的能力。

改法：

```cpp
mosquitto_connect_async(mosq_, host, port, keepalive);
mosquitto_loop_start(mosq_);      // 启动后台网络线程
```

同时删掉 `Poll()` 里的 `mosquitto_loop()` 调用——后台线程已经在驱动网络，手动再调会争抢同一个 socket。代价是回调跑到后台线程，共享数据都要加锁。

## 3. 日志出现重复行

修完上一个问题后：

```
[INFO ] DeviceClient 已启动，数据源：MqttSource(localhost:1883)
[INFO ] DeviceClient 已启动，数据源：MqttSource(localhost:1883)
```

先查是不是上次测试的日志残留（文件创建时间、有没有旧时间戳），排除了。
再查代码里是不是写了两遍，`grep` 发现只有一处调用。

`std::ofstream` 和 `std::cerr` 都不是线程安全的。现在主线程和 MQTT 后台线程会同时写，流缓冲区被交错破坏。

改法：给 `Logger` 加 `std::mutex`，`Log()` 里整个输出过程持锁。

```cpp
// logger.h
mutable std::mutex mutex_;   // mutable：Log 不改成员，但要加锁

// logger.cpp
std::lock_guard<std::mutex> lock(mutex_);
std::cerr << line << '\n';
if (file_.is_open()) { file_ << line << '\n'; file_.flush(); }
```

改完重测：19 行日志，0 重复。

## 4. reconnect_delay_set 的单位

`mosquitto_reconnect_delay_set(mosq_, 1, 30, true)` 两个参数单位是**秒**。
我按毫秒传了 `1000`，等于等 1000 秒才重连，实测断线后 42 秒都没恢复。

## 5. 下行命令污染遥测通道

命令走了和遥测同一条队列，被 `DeviceClient` 当数据帧解析：

```
[INFO ] >>> 执行喂食：投喂 2 克
[WARN ] 丢弃一帧坏数据：报文缺少 device_id 字段 | 原始内容: {"cmd":"feed","amount":2}
```

命令是事件，遥测是数据流，不该共用一条通道。加 `config.queue_downlink`（默认 false），命令只触发 `OnCommand` 回调，不入队。

## 6. 请求订阅的时机

订阅放在 `Open()` 里只调一次的话，断线重连后不会恢复——TCP 重连了但会话状态不在。

放在连接成功的回调里（`HandleConnect`），每次连上都订阅一次，重连后自动恢复：

```
19:11:21.788 [INFO ] 已连接到 broker：localhost:1883（第 2 次成功）
19:11:21.788 [INFO ] 已订阅下行主题：dev/fish-tank-01/cmd（QoS 1）
```

## 7. 持锁调用虚函数会死锁

`HandleMessage()` 里原本在持锁状态下调用 `OnCommand()`，而子类的 `OnCommand` 里会调 `Publish()`，`Publish()` 又要拿同一把锁。

改成先更新统计、释放锁，再调 `OnCommand()`，最后重新加锁入队。

## 8. MqttConfig 不能写成嵌套类

```cpp
class MqttSource {
    struct Config { std::string broker_host = "localhost"; ... };
    explicit MqttSource(Config config = Config{});   // GCC 16 报错
};
```

```
error: default member initializer for 'broker_host' required before the end of its enclosing class
```

把 `Config` 提到命名空间层级就没问题，类里用 `using Config = MqttConfig;` 保留原来的写法。

## 9. 命令行编译正常，编辑器却找不到 mosquitto.h

命令行编译一切正常，VSCode 里 `#include "iotd/mqtt_source.h"` 却报"检测到 #include 错误，
请更新您的 includePath"，并连带报 `无法打开源文件 "mosquitto.h"`。

排查用 ninja 直接打印真实编译命令：

```bash
ninja -C build -t commands | grep mqtt_demo.cpp
```

```
c++.exe -ID:/Matt/JobHunt/iot-device-sdk/include -g -std=c++17 -Wall -Wextra ...
```

只有项目自己的 include，`C:/msys64/ucrt64/include` 不见了。但 `pkg-config --cflags libmosquitto`
明明输出 `-IC:/msys64/ucrt64/include`，`CMakeCache.txt` 里 `MOSQUITTO_INCLUDE_DIRS` 也确实是它。

原因在 CMake 的一个优化：它配置阶段会记录编译器的隐式搜索路径，写进
`CMAKE_CXX_IMPLICIT_INCLUDE_DIRECTORIES`（`build/CMakeFiles/*/CMakeCXXCompiler.cmake`）：

```
C:/msys64/ucrt64/include/c++/16.2.0; ...; C:/msys64/ucrt64/include
```

MSYS2 把第三方库头文件都装在工具链自己的 include 目录里，而该目录已经在隐式列表内，
于是 CMake 认为不需要再传 `-I`，生成命令时把它去掉了。GCC 自己知道去哪找，所以编译没问题。

问题出在 `compile_commands.json` 也照抄了这份"省略后"的命令，插件的 IntelliSense 只读这个文件，
看不到隐式路径，于是画红线。

改法：在 `.vscode/settings.json` 里补上 `C_Cpp.default.includePath`，把
`C:/msys64/ucrt64/include` 手动加进去。编译侧不用动。

同类问题的判别方法：凡是"编译过了但编辑器报错"，先用 `ninja -t commands` 看真实参数，
再对照 `CMAKE_CXX_IMPLICIT_INCLUDE_DIRECTORIES`，就能判断是工具链隐式路径被省略了。
