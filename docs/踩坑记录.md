# 踩坑记录

## 1. 程序启动即退出，无输出

退出码 `-1073741511`

转十六进制是 `0xC0000139`，`STATUS_ENTRYPOINT_NOT_FOUND`，用 objdump 查依赖：

```bash
objdump -p libmosquitto.dll | grep "DLL Name"
```

`libmosquitto.dll` 还依赖 `libcrypto-3-x64.dll`、`libssl-3-x64.dll`、`libwinpthread-1.dll`，
exe 自己还需要 `libstdc++-6.dll`、`libgcc_s_seh-1.dll`

我最初只复制了 `libmosquitto.dll` 一个，依赖是传递的，只复制直接依赖不够

改法：`CMakeLists.txt` 里 POST_BUILD 批量复制 6 个 DLL，另外加 `-static-libgcc -static-libstdc++` 去掉两个 GCC 运行库依赖

## 2. 断线后不重连

broker 挂掉后不重连，而且每 20ms 往日志刷一条：

```
[ERROR] 数据源错误：MQTT 连接异常：The client is not currently connected.
```

原因是我最初用手动网络循环：

```cpp
const int rc = mosquitto_loop(mosq_, 0, 1);   // 主循环里每 20ms 调一次
```

`mosquitto_loop()` 不处理重连，查 `mosquitto.h` 第 1207-1216 行：

> The two recommended approaches are to use either **mosquitto_loop_forever** or **mosquitto_loop_start**.
> Use this function [loop_start] when you have other tasks you need to run at the same time as the MQTT client.

自动重连是 `loop_forever` / `loop_start` 提供的能力

改法：

```cpp
mosquitto_connect_async(mosq_, host, port, keepalive);
mosquitto_loop_start(mosq_);      // 启动后台网络线程
```

同时删掉 `Poll()` 里的 `mosquitto_loop()` 调用——后台线程已经在驱动网络，手动再调会争抢同一个 socket，代价是回调跑到后台线程，共享数据都要加锁

## 3. 日志出现重复行

修完上一个问题后：

```
[INFO ] DeviceClient 已启动，数据源：MqttSource(localhost:1883)
[INFO ] DeviceClient 已启动，数据源：MqttSource(localhost:1883)
```

先查是不是上次测试的日志残留（文件创建时间、有没有旧时间戳），排除了
再查代码里是不是写了两遍，`grep` 发现只有一处调用

`std::ofstream` 和 `std::cerr` 都不是线程安全的，现在主线程和 MQTT 后台线程会同时写，流缓冲区被交错破坏

改法：给 `Logger` 加 `std::mutex`，`Log()` 里整个输出过程持锁

```cpp
// logger.h
mutable std::mutex mutex_;   // mutable：Log 不改成员，但要加锁

// logger.cpp
std::lock_guard<std::mutex> lock(mutex_);
std::cerr << line << '\n';
if (file_.is_open()) { file_ << line << '\n'; file_.flush(); }
```

改完重测：19 行日志，0 重复

## 4. reconnect_delay_set 的单位

`mosquitto_reconnect_delay_set(mosq_, 1, 30, true)` 两个参数单位是**秒**
我按毫秒传了 `1000`，等于等 1000 秒才重连，实测断线后 42 秒都没恢复

## 5. 下行命令污染遥测通道

命令走了和遥测同一条队列，被 `DeviceClient` 当数据帧解析：

```
[INFO ] >>> 执行喂食：投喂 2 克
[WARN ] 丢弃一帧坏数据：报文缺少 device_id 字段 | 原始内容: {"cmd":"feed","amount":2}
```

命令是事件，遥测是数据流，不该共用一条通道，加 `config.queue_downlink`（默认 false），命令只触发 `OnCommand` 回调，不入队

**后续：这个开关后来整个删掉了**

`queue_downlink` 能成立的前提是"MQTT 也是一路数据源"，而那个前提本身就不对 —— 云平台不会产生传感器读数

正确的形状是 MQTT 只当出口，数据源交给模拟器/串口。改完之后 `queue_downlink` 无处可挂，连同待投递队列一起删除，这个坑从根上不存在了

教训：**给一个不该存在的设计加开关，只是在给错误续命。开关越多，越说明当初的分层没想清楚**

## 6. 请求订阅的时机

订阅放在 `Open()` 里只调一次的话，断线重连后不会恢复——TCP 重连了但会话状态不在

放在连接成功的回调里（`HandleConnect`），每次连上都订阅一次，重连后自动恢复：

```
19:11:21.788 [INFO ] 已连接到 broker：localhost:1883（第 2 次成功）
19:11:21.788 [INFO ] 已订阅下行主题：dev/fish-tank-01/cmd（QoS 1）
```

## 7. 持锁调用虚函数会死锁

`HandleMessage()` 里原本在持锁状态下调用 `OnCommand()`，而子类的 `OnCommand` 里会调 `Publish()`，`Publish()` 又要拿同一把锁

改成先更新统计、释放锁，再调 `OnCommand()`，最后重新加锁入队

## 8. MqttConfig 不能写成嵌套类

```cpp
class MqttSource {
    struct Config { std::string broker_host = "localhost"; ... };
    explicit MqttSource(Config config = Config{});   // GCC 16 报错
};
```

```
error: default member initializer for 'broker_host' required before the end of its enclosing class
```

把 `Config` 提到命名空间层级就没问题，类里用 `using Config = MqttConfig;` 保留原来的写法

## 9. 命令行编译正常，编辑器却找不到 mosquitto.h

命令行编译一切正常，VSCode 里 `#include "iotd/mqtt_sink.h"` 却报"检测到 #include 错误，
请更新您的 includePath"，并连带报 `无法打开源文件 "mosquitto.h"`

排查用 ninja 直接打印真实编译命令：

```bash
ninja -C build -t commands | grep mqtt_demo.cpp
```

```
c++.exe -ID:/Matt/JobHunt/iot-device-sdk/include -g -std=c++17 -Wall -Wextra ...
```

只有项目自己的 include，`C:/msys64/ucrt64/include` 不见了，但 `pkg-config --cflags libmosquitto`
明明输出 `-IC:/msys64/ucrt64/include`，`CMakeCache.txt` 里 `MOSQUITTO_INCLUDE_DIRS` 也确实是它

原因在 CMake 的一个优化：它配置阶段会记录编译器的隐式搜索路径，写进
`CMAKE_CXX_IMPLICIT_INCLUDE_DIRECTORIES`（`build/CMakeFiles/*/CMakeCXXCompiler.cmake`）：

```
C:/msys64/ucrt64/include/c++/16.2.0; ...; C:/msys64/ucrt64/include
```

MSYS2 把第三方库头文件都装在工具链自己的 include 目录里，而该目录已经在隐式列表内，
于是 CMake 认为不需要再传 `-I`，生成命令时把它去掉了，GCC 自己知道去哪找，所以编译没问题

问题出在 `compile_commands.json` 也照抄了这份"省略后"的命令，插件的 IntelliSense 只读这个文件，
看不到隐式路径，于是画红线

改法：在 `.vscode/settings.json` 里补上 `C_Cpp.default.includePath`，把
`C:/msys64/ucrt64/include` 手动加进去，编译侧不用动

同类问题的判别方法：凡是"编译过了但编辑器报错"，先用 `ninja -t commands` 看真实参数，
再对照 `CMAKE_CXX_IMPLICIT_INCLUDE_DIRECTORIES`，就能判断是工具链隐式路径被省略了

## 10. mqtt_demo退出卡顿，按两次 Ctrl+C才能退出

按一次 Ctrl+C 程序不退出，再按一次才回到提示符，而且从来没有打印过那张收尾统计表

先数日志：8 次运行里 `MQTT 已断开` 出现 0 次，说明收尾流程压根没走完

```bash
grep -c "MQTT 已断开" build/mqtt_demo.log
```

怀疑过终端（MSYS2 的 mintty 把 Ctrl+C 转发给原生 exe 有已知问题），换到 Windows Terminal 复现，一样

于是写最小复现程序，把 `MqttSource::Close()` 那三步拆开计时，做对照实验——
同一份代码，只换 broker 是否存在：

```
case A（broker 在跑，连接成功）:  loop_stop RETURNED after 13011 ms
case B（没有 broker，连接失败）:  loop_stop RETURNED after 0 ms
```

**13 秒 ≈ keepalive 15 秒**，而且方向和直觉相反：连接**正常**时才会卡

原因：后台线程平时阻塞在 `poll()` 上，poll 超时是按 keepalive 算的。
`force=true` 本该关掉 socket 把 poll 打断，但它在 Windows 上不生效
（libmosquitto issue #117），于是 `loop_stop` 里的 join 只能干等线程自己醒过来

改法：把 `disconnect` 提到 `loop_stop` 之前，它会主动唤醒线程

```cpp
// mqtt_source.cpp  Close()
if (connected_.load()) {
    ::mosquitto_disconnect(mosq_);                  // 先唤醒线程
    connected_ = false;
}
::mosquitto_loop_stop(mosq_, /*force=*/true);       // 再停线程
::mosquitto_destroy(mosq_);                         // 最后销毁
```

实测：

```
先 loop_stop 再 disconnect → 13011 ms
先 disconnect 再 loop_stop → 0 ms
```

改完按一次 Ctrl+C，等十几秒后正常退出并打印统计表：

```
22:06:26.479 [INFO ] ↑ 上报成功 #2 temp=25C humid=62% 开机6301ms
22:06:42.022 [INFO ] 与 broker 的连接已正常关闭      ← 间隔 15.5 秒
22:06:42.023 [INFO ] MQTT 已断开：MqttSource(localhost:1883)（统计：连接成功 1 次，收到 0 条，发布成功 2 条）
```

判别方法：凡是"程序不响应 Ctrl+C / 退出卡顿"，先看日志里收尾那几行有没有打出来，
就能区分是"信号没送达"还是"卡在收尾里"

## 11. iotd_tests 中文输出乱码

```
===== iotd 娴嬭瘯寮€濮?=====
[娴嬭瘯] JSON 鍩虹绫诲瀷
```

`device_sim`、`mqtt_demo`、`iot-debug` 都正常，只有 `iotd_tests` 乱码

先确认字节本身有没有坏，把输出重定向到管道再看：

```bash
./iotd_tests | od -An -tx1
```

```
3d 3d 3d 3d 3d 20 69 6f 74 64 20 e6 b5 8b e8 af 95 ...
                            ^^^^^^^^^^^^^^^^^^^^^^^^^ 测试 = 标准 UTF-8
```

源文件也确认过是 UTF-8（`file tests/test_json.cpp`），也就是说程序吐出来的是**正确的 UTF-8**，
错的是"谁来解码"

乱码的来源是控制台按 GBK（代码页 936）去解读 UTF-8 的字节：

| 字节对 | 按 GBK 解出来 |
|---|---|
| `E6 B5` | 娴 |
| `8B E8` | 嬭 |
| `AF 95` | 瘯 |

字符串尾部那个 `?` 是关键证据：`开始` 的字节是 `E5 BC 80 E5 A7 8B 20`，
最后的 `8B 20` 里 `8B` 是 GBK 首字节、空格 `20` 不是合法尾字节，
解码器用一个 `?` 顶替并**把那个空格吃掉了**，所以 `开始 =====` 变成了 `濮?=====`

原因：另外三个程序在 `main()` 开头都调了 `::SetConsoleOutputCP(CP_UTF8)`，
把控制台输出代码页改成 65001，`tests/test_json.cpp` 漏了这一步

```cpp
#if defined(_WIN32)
    ::SetConsoleOutputCP(CP_UTF8);
#endif
```

**这个坑最坑人的地方**：先跑一遍 `device_sim` 再跑 `iotd_tests`，乱码就消失了

因为 `SetConsoleOutputCP` 改的是**控制台窗口**的属性，不是进程的属性。
`device_sim` 退出后窗口仍然停在 65001，后面的程序白捡一个正确显示——
在同一个窗口里**先跑过谁，会决定后面程序的输出对不对**，这类 bug 极难复现

判别方法：两个窗口各敲一次 `chcp.com`，显示 936 的就是会乱码的那个。
输出被重定向到文件或管道时不受影响（没有控制台，也就没有代码页），文件里永远是正确 UTF-8

## 12. sleep_for(20ms) 实际睡了 31ms

`mqtt_demo` 主循环注释写的是"每 100 轮（约 2 秒）"，实测上报间隔 3.12 秒

在主循环里加计时量 1000 轮的耗时，做两个对照：

| `sleep_for` 参数 | 1000 轮耗时 | 每轮平均 |
|---|---|---|
| `20ms` | 31242 ms | 31.24 ms |
| `0ms` | 2 ms | 0.002 ms |

按 `31250 − 20000 = 11250` 去算会得出"循环体每轮要 11.25ms"，
但 `0ms` 那组总耗时只有 2ms，**循环体几乎不花时间**，这个减法根本不成立

真正的原因是 Windows 的调度节拍。默认节拍约 15.6ms（64 Hz），被挂起的线程
**只能在节拍点上被唤醒**，所以 `sleep_for` 的时长会被向上取整到节拍的整数倍

实测阶梯（同一个程序，只换参数）：

```
请求 1ms  / 5ms  / 10ms  → 都是 15.6ms 左右
请求 16ms / 20ms / 25ms  → 都是 31.1ms 左右
请求 32ms / 50ms         → 46.9ms / 62.3ms
```

**请求 16ms 和请求 20ms 拿到的耗时一模一样**，所以把参数调小根本没用。
20ms 落在"两个节拍"那一档，31.25ms 就是这么来的

100 轮 × 31.25ms = 3125ms ≈ 3.12 秒，和日志里量到的 3120ms / 3129ms 对得上

一个容易量错的地方：**计时起点必须紧贴 `while` 的前一行**。
图省事用 `main` 开头的时间戳，会把 `client.Start()`（连 broker + 订阅，实测 9~15ms）
一起算进去——在 31000ms 里看不出来，但在 2ms 量级的对照组里，误差比测量值还大

判别方法：`sleep_for` 的参数是**下限**不是实际耗时，而且这个"下限"还受系统节拍限制。
需要精确定时用 `sleep_until` 基于绝对时刻，误差才不累积

## 13. 基类中默认初始化嵌套类，GCC 报 default member initializer

想按 STL 的习惯把配置结构体写成嵌套类 `MqttSource::Config`，结果这行编不过：

```cpp
class MqttSource : public IDataSource {
public:
    struct Config {
        std::string broker_host = "localhost";
        int broker_port = 1883;
    };
    explicit MqttSource(Config config = Config{});   // ← 报错
};
```

```
error: default member initializer for 'broker_host' required before the end of
       its enclosing class
```

把各种写法都编了一遍（GCC 16.2.0，c++17 / c++20 / c++23 行为一致）：

| 写法 | 结果 |
|---|---|
| 嵌套 + DMI + `= Config{}` | 报错 |
| 嵌套 + DMI + **`Config() {}`** + `= Config{}` | **通过** |
| 嵌套 + DMI + `Config() = default;` + `= Config{}` | 报错 |
| 嵌套 + 不带 DMI（改在构造函数初始化列表里赋值）+ `= Config{}` | 通过 |
| 嵌套 + DMI + `= Config()` | 报错 |
| 嵌套 + DMI + 删掉默认实参，改 `Foo() : Foo(Config{}) {}` | 通过 |
| 命名空间层级 + DMI + `= Config{}` | 通过 |

**根本原因**：默认实参合不合法，会决定这个构造函数算不算"默认构造函数"，
进而决定编译器要不要再隐式声明一个默认构造函数。所以必须**提前**知道
`Config` 是不是默认可构造 —— 而这取决于它的 DMI，DMI 是 complete-class
context 要等类完整才解析，嵌套类又要等基类完整，绕成了循环依赖

`Config() {}` 能过、`Config() = default;` 不能过，差别在于前者是**断言**
"我默认可构造"，后者是**待推导**（可能因为成员定义不合法而被 delete）

查下来这是 GCC 的已知 bug：[88165](https://gcc.gnu.org/bugzilla/show_bug.cgi?id=88165)
（已标记为 [96645](https://gcc.gnu.org/bugzilla/show_bug.cgi?id=96645) 的重复，而 96645 仍是 ASSIGNED 未修），
标签 `[14/15/16/17 Regression]`，关键词 `rejects-valid`，还挂着标准缺陷报告 CWG 2335。
连 `std::variant` 自己的默认构造函数都中招，这也是它被算作 Regression 的原因

注意这只是"嵌套类 + DMI + 默认实参"三样凑齐才触发。
本项目里 `MqttSource::Stats` 同样是带 DMI 的嵌套类，但它没被当默认实参，一直好好的

**标准库是怎么绕开的**（查的本机 libstdc++ 16.2.0）：

- `vector<T>::iterator` 是 `typedef __gnu_cxx::__normal_iterator<...>` —— 嵌套名，真类型在命名空间层级
- `locale::facet` / `locale::id` / `locale::_Impl`（`bits/locale_classes.h:405/517/560`）、
  `path::_Codecvt` / `path::iterator`（`bits/fs_path.h:879/946`）—— 类内只声明、类外定义
- `vector` / `map` 的默认实参只用 `allocator_type`（命名空间层级的 typedef）或模板参数

**没有一条是"嵌套类按值当默认实参"**

顺手试了"类内声明 + 类外定义"这条路，对这个场景没用：

```cpp
class Foo {
public:
    struct Config;
    explicit Foo(Config c = Config{});   // error: invalid use of incomplete type
    Config* c_;                          // locale 只用指针，所以它没事
};
class Foo::Config { std::string host = "localhost"; };
```

默认实参写在类里面，那个位置 `Config` 还没定义完。`locale` 之所以能用这个模式，
是因为它**从不把 `_Impl` 按值传**，只用 `_Impl*` —— 指针和引用不要求类型完整

**当前选择**：`MqttConfig` 放命名空间层级，类里用 `using Config = MqttConfig;` 保留 `MqttSource::Config` 这种写法

判别方法：凡是"嵌套类 + 默认成员初始化器 + 出现在基类的默认实参里"这三样凑齐，
先试给嵌套类加一个**用户提供的**默认构造函数（`Config() {}`，注意不是 `= default`）；
或者直接将嵌套类抽出来在命名空间定义，然后在基类中使用别名；

## 14. 日志写着"上报成功 #1 开机3145ms"，报文里却没有这两个字段

`mqtt_demo` 跑起来日志一切正常：

```
2026-10-14 18:16:26.747 [INFO ] ↑ 上报成功 #1 temp=24.5C humid=61% 开机3145ms
```

另开一个窗口订阅真实主题，抓到的载荷是：

```
dev/fish-tank-01/up {"device_id":"fish-tank-01","timestamp_ms":1791972986747,"temp":24.50,"humid":61.00,"light_lux":301}
```

`seq` 和 `uptime_ms` 都不见了

原因在 `OnTelemetry` 这一行：

```cpp
source.PublishTelemetry(msg.reading, error);   // 只传了读数
```

`DeviceClient` 生成 `DeviceMessage` 时贴好的 `sequence` / `uptime_ms`，
在 `MqttSink` 那个发布函数的门口被挡掉了——它的参数只收 `SensorReading`，
而 `SensorReading` 里根本没有这两个字段

**为什么单测抓不到**：`DeviceClient::ParseFrame`、`DeviceClient::PollOnce`、
`MqttSink::Publish` 三段各自都是对的，丢信息的是**它们之间的拼接处**。
这类问题只能靠端到端抓一次真实报文发现

**为什么日志反而掩盖了它**：日志打印的是 `DeviceMessage`（完整的），
发出去的是它的一个子集。读到"上报成功 #1 开机3145ms"的人会自然认为这两个字段
跟着发出去了，只有抓包能证伪——**日志描述的对象和实际传输的对象不是同一个**

改法是删掉"只收读数"的那个重载，只留一个入口
`MqttSink::Publish(const DeviceMessage&, std::string&)`。
**签名本身就是防线**：调用方拿不到只传读数的机会，元数据就丢不了

（这个函数后来还改了名和位置：从 `MqttSource::PublishTelemetry` 变成
`MqttSink::Publish`，因为它成了 `ITelemetrySink` 接口的实现）

改完之后日志和报文对上了（同一次运行）：

```
2026-10-14 18:16:26.747 [INFO ] ↑ 上报成功 #1 temp=24.5C humid=61% 开机3145ms
dev/fish-tank-01/up {"device_id":"fish-tank-01","timestamp_ms":1791972986747,"uptime_ms":3145,"seq":1,"temp":24.50,"humid":61.00,"light_lux":301}
```

判别方法：发布函数如果只收"数据"不收"消息"，就是在邀请调用方把元数据丢掉。

## 15. 把 MQTT 从"数据源"改回"出口"

**症状**：`mqtt_demo` 跑了几百轮，退出时统计写着

```
DeviceClient 已停止。统计：收到 0 帧，成功 0 帧，解析失败 0 帧，数据源错误 0 次
```

当时以为这是正常的（`queue_downlink` 默认 false，命令不进队列），还在文档里写了一句"收到 0 帧是预期的"

**真正的问题**：`DeviceClient` 的入站那一半从来没被用过
`MqttSource` 实现了 `IDataSource`，却永远产不出数据 —— 因为**云平台不会产生传感器读数**

**它怎么变成这样的**（每一步都合理，合起来就错了）：

1. 第一期只有入站，`MockSource` / `SerialPortSource` 本来就是只读的，所以 `IDataSource` 只设计成 4 个读函数 —— 当时完全正确
2. 第二期接 MQTT，发现 MQTT 是双向的，需要一个"写"的能力
3. 最省事的做法：在 `MqttSource` 上加一个发布方法，顺手也让它实现 `IDataSource`（"三种数据源可替换"听起来很漂亮），应用层已有的回调顺手调那个发布方法

**结果**：

- `MqttSource` 挂着一块"数据源"的牌子，实际不干活
- 出站方向绕了一圈：`DeviceClient` 打包 → 回调 → 回到 `mqtt_demo` → 再调 `MqttSource` 发布
- `DeviceClient` 在 `mqtt_demo` 里退化成一个只贴标签的中间商（它的入站半身空转）

**改法**：

| | 改之前 | 改之后 |
|---|---|---|
| 接口 | `IDataSource` 一个接口、三个实现 | `IDataSource`（进）+ `ITelemetrySink`（出），各两个实现 |
| `DeviceClient` | 持有 `IDataSource&` + 一个 `std::function` 回调 | 持有 `IDataSource&` + `ITelemetrySink&` |
| 出站路径 | 回调 → 应用层 → 再发 | `sink_.Publish()` 一条直线 |
| `MqttSource` | 既当数据源又当出口 | 改名 `MqttSink`，只当出口 |
| `mqtt_demo` 的数据从哪来 | main 里手写 `24.0 + (n%5)*0.5` | `MockSource` 造，和串口同一种东西 |

**改完之后**：`mqtt_demo` 才第一次成为一个完整的网关（传感器 → 解析校验 → 上报），
`DeviceClient` 的入站半身终于有数据流过，坏帧、范围校验、统计这些代码也第一次真正被执行

**教训**：

- 一个类**同时实现两个接口**没问题（标准库的 `std::iostream` 就是），有问题的是**只申报一个身份却干两件事**
- "能不能替换"不是抽象的卖点，要看**替换的是什么**：模拟器和串口是同一类东西（都产生读数），MQTT 不是
- 出现"为了兼容某个场景加一个开关"的时候，先回头看看**那个场景该不该存在**
