### 2.1 路子 A：手动编译（10 分钟，立刻见效）

不需要 CMake，直接用你已有的 g++。在 PowerShell 里执行：

```powershell
# 把 MinGW 加进 PATH（每个新窗口都要执行一次）
$env:PATH = 'D:\VScode\Environment\mingw64-14.2.0\bin;' + $env:PATH

cd D:\Matt\JobHunt\iot-device-sdk

# 编译：把所有 .cpp 一起交给编译器
g++ -std=c++17 -Wall -Wextra -I include -o iot-debug.exe `
  src\json.cpp src\logger.cpp src\mock_source.cpp `
  src\serial_port_source.cpp src\device_client.cpp `
  tools\iot_debug_main.cpp
```

逐段解释这条命令，**每一条你都要懂**：

| 片段 | 作用 |
|---|---|
| `g++` | 调用 GNU C++ 编译器 |
| `-std=c++17` | 使用 C++17 标准（我们用到了 `std::variant`、`std::optional`） |
| `-Wall -Wextra` | 打开所有常见警告。**看到警告要当成错误处理**，否则以后会花十倍时间debug |
| `-I include` | 把 `include` 目录加入头文件搜索路径。这样 `#include "iotd/json.h"` 才能找到 |
| `-o iot-debug.exe` | 指定输出的可执行文件名 |
| 后面一串 `src\*.cpp` | **要编译的源文件清单**。注意：编译器不会自动找，必须一个个列出来 |
| 反引号 `` ` `` | PowerShell 的换行续行符（让一条长命令分多行写） |

编译成功后运行：

```powershell
.\iot-debug.exe mock 500        # 用模拟数据源跑，每 500ms 一帧
# 按 Ctrl+C 退出
```

你会看到类似这样的输出：

### 2.2 路子 B：装 CMake 走正规流程（1-2 小时，一次投入长期受益）

为什么值得装？因为后面要接 MQTT 库时，手动编译会变成灾难（要处理几十个源文件、库路径、链接顺序）。CMake 就是解决这个问题的。

**推荐方式：MSYS2**（比装整套 Visual Studio 轻得多，约 100 MB）

1. 到 [msys2.org](https://www.msys2.org/) 下载安装器并安装（默认装到 `C:\msys64`）
2. 打开 **MSYS2 UCRT64** 终端（注意：**不是** MINGW64，也不是 MSYS2 MSYS）
   > **为什么必须是 UCRT64？**（2026-09-30 核实自 [MSYS2 官方文档](https://www.msys2.org/docs/environments/)）
   > - 官方明确写："If you are unsure, go with **UCRT64**"
   > - 2022-10-29 MSYS2 就把默认环境从 MINGW64 换成了 UCRT64
   > - **2026-03-15 MINGW64 被正式弃用**，原文："no new packages will be added to this environment"，官方建议迁到 UCRT64 或 CLANG64
   > - 你现有的 MinGW-builds GCC 14.2.0 也是 **UCRT** 版（它的 sysroot 路径里带 `ucrt` 字样），两者同属一个 C 运行库阵营
3. **先换国内镜像加速**（否则下载可能很慢）：
   ```bash
   # 编辑 /etc/pacman.d/mirrorlist.ucrt64，在最上面加：
   # Server = https://mirrors.tuna.tsinghua.edu.cn/msys2/mingw/ucrt64/
   # Server = https://mirrors.ustc.edu.cn/msys2/mingw/ucrt64/
   # 改完先做一次全面更新：
   pacman -Syu
   ```
4. 安装工具链（**注意包名里的 `ucrt`，别抄成 `mingw64`**）：
   ```bash
   pacman -S --needed --noconfirm \
          mingw-w64-ucrt-x86_64-toolchain \
          mingw-w64-ucrt-x86_64-cmake \
          mingw-w64-ucrt-x86_64-ninja \
          mingw-w64-ucrt-x86_64-gdb \
          mingw-w64-ucrt-x86_64-mosquitto
   ```
   > **`--noconfirm` 是必加的。** 不加它，pacman 会停在两个交互提问上：
   > ① `:: There are N members in group mingw-w64-ucrt-x86_64-toolchain: ... Enter a selection (default=all):`
   > ② `:: Proceed with installation? [Y/n]`
   > 前者**直接回车**就装全部成员，后者按 `Y`。加了 `--noconfirm` 则全部自动选默认值，一条命令跑完不打断。
   >
   > `mosquitto` 是**第二期接 MQTT 时要用的**，现在一次装完，省得再折腾一遍镜像。
   > 这是 UCRT64 路线最大的好处：**MQTT 库有现成的 pacman 包**（见第 5 节）。
5. **先验证，再动项目**（这一步不能省）：
   ```bash
   cmake --version     # 应输出版本号（≥3.20）
   ninja --version
   g++ --version       # 应显示 GCC 版本，且 /ucrt64/bin 在 PATH 里
   which g++           # 确认是 /ucrt64/bin/g++ 而不是别的
   ```
6. 构建项目：
   ```bash
   cd /d/Matt/JobHunt/iot-device-sdk
   mkdir -p build && cd build
   cmake .. -G Ninja -DCMAKE_BUILD_TYPE=Debug
   ninja
   ```

**CMake 三个命令的心智模型**（很多人用了几年都没搞懂）：

```
源码目录                      构建目录(build/)
├─ CMakeLists.txt  ──①cmake──▶  ├─ Makefile / build.ninja   ← 真正的构建脚本
├─ src/*.cpp                    ├─ CMakeCache.txt           ← 记录你的配置（编译器路径等）
└─ include/                     └─ iot-debug.exe            ← 产物
                    ②ninja ────▶
```

- `cmake ..` **不是编译**，它只是"读 CMakeLists.txt，生成构建脚本"，这叫 configure 阶段
- `ninja` 才是真正编译（等价于自动化的 `g++ ...`）
- **改代码后只需要重跑 `ninja`**，不用再 `cmake ..`；只有改了 `CMakeLists.txt` 才需要重新 configure
- `build/` 目录可以随时整个删掉重新生成——**它里面没有你的源码，别怕**

> ⚠️ 路径坑：**绝对不要把项目放在带中文的路径下**。CMake、Ninja、MSVC 对非 ASCII 路径支持都很差。你现在的 `D:\Matt\JobHunt\` 没问题。

## 1. 代码全景：这些文件是怎么串起来的

先建立整体印象，再看细节。

### 1.1 两个视角

**视角一：编译时（谁生成什么）**

```
src/*.cpp  ──编译──▶  目标文件(.o)  ──打包──▶  libiotd_core.a (静态库)
                                                      │
                       tools/iot_debug_main.cpp ──链接─┤
                     examples/device_sim.cpp  ──链接─┤
                          tests/test_json.cpp ──链接─┘
                                                      ▼
                                        iot-debug.exe / device_sim.exe / iotd_tests.exe
```

**为什么要先做成"库"再链接成 exe？**
因为三个程序要用同一套代码。如果不用库，你得把 `json.cpp` 编译三遍、维护三份拷贝。库的本质就是**可复用的能力包**——这也正是 SDK 的定义。

**视角二：运行时（数据怎么流动）**

```
① MockSource.Poll() 或 SerialPortSource.Poll()
        │  "给你一帧文本：{"device_id":"fish-tank-01","temp":25.6}"
        ▼
② DeviceClient.PollOnce()          ← 驱动器，每次主循环调用一次
        │
③ DeviceClient::ParseFrame()
        │   ├─ json::Parse(frame)          ← 手写解析器，坏数据抛异常
        │   └─ 业务校验（温度范围、必填字段）
        │
        ├──失败──▶ LOG_WARN 打印错误 + 原始内容，统计 parse_failed++，程序继续
        │
        └──成功──▶ ④ TelemetryHandler 回调
                        ├─ device_sim：打印 + 统计
                        └─ iot-debug：打印到屏幕
                                 │
                        ⑤ Logger 同时写屏幕和 .log 文件
```

**关键理解**：`DeviceClient` 不打印也不存文件，它只负责"把一帧文本变成 `DeviceMessage` 结构体"，然后交给回调。**做什么由回调决定**。这解释了为什么接 MQTT 时不用改 `DeviceClient`——只要换一个回调就行。

## 3. 逐文件详解（按阅读顺序）

### 3.1 `types.h` — 先统一数据类型

**作用**：定义 `SensorReading`（一条读数）和 `DeviceMessage`（一条完整报文）。

**为什么单独放一个文件？** 因为 `MockSource` 产生它、`DeviceClient` 消费它、JSON 解析器填充它。如果定义在某个 `.cpp` 里，别人用不了。

**要学的东西**：
- `struct` 与默认成员初始化器（`double temperature_c = 0.0;`）——**防"未初始化垃圾值"这个新手头号 bug**
- `namespace` 为什么存在
- `inline` 函数为什么能写在头文件里（不加 `inline` 会"符号重复定义"）

### 3.2 `json.h` / `json.cpp` — 手写解析器（本项目技术含量最高的文件之一）

**作用**：把 `{"device_id":"x","temp":25.6}` 这段文本变成一个可以 `GetNumber(root,"temp")` 取值的结构。

**为什么手写而不用 nlohmann/json？** 三个理由，都是刻意的：
1. 你需要看懂每一行，而不是把库当黑盒
2. 零依赖 = 你今天就能跑起来，不会卡在下载依赖上
3. 面试能讲的东西完全不同：手写解析器可以聊**递归下降、类型安全、错误定位**

**核心技术点**：

**(1) `std::variant` —— 一个变量装多种类型**

JSON 的一个值可能是字符串、数字、布尔、对象、数组。C++ 是静态类型语言，一个变量只能一种类型。`std::variant<std::string,double,bool,Object,Array>` 就是"这些里的一种"，它是**类型安全的 union**。

**(2) 递归下降解析 —— 因为 JSON 语法本身是递归的**

```
值   := 字符串 | 数字 | 布尔 | 对象 | 数组
对象 := { 键值对列表 }
值   := …… 又回到开头
```

数据结构是递归的，所以处理它的代码也递归。`ParseObject()` 里调用 `ParseValue()`，`ParseValue()` 又可能调回 `ParseObject()`。

**(3) 错误必须带位置**

```cpp
throw ParseError("对象的键必须是字符串", pos_);
```

`pos_` 是当前扫描到的字符下标。**这是"能用的工具"和"玩具"的分界线**——客户给你一段报文说"解析不了"，你能立刻告诉他"第 69 个字符有问题"。

**(4) 一个经典 C++ 坑：`std::isspace` 的参数类型**

```cpp
std::isspace(static_cast<unsigned char>(text_[pos_]))   // 必须这样写
```

如果直接传 `char`，当字符值 > 127（比如中文 UTF-8 字节）时会被当成负数，**行为未定义**。这是面试常问的细节。

### 3.3 `logger.h` / `logger.cpp` — 日志

**作用**：同时输出到屏幕和文件，带时间戳和级别。

**要学的东西**：
- **单例模式**：`Logger::Instance()`，构造函数私有化 + 静态局部变量。C++11 起静态局部变量初始化是线程安全的
- **RAII 思想**：`std::ofstream` 成员在对象析构时自动关闭文件
- **日志宏**：`LOG_INFO("temp=" << t)` 用 `std::ostringstream` 把各种类型拼成字符串
- **每行 flush**：程序崩溃时缓冲区里没落盘的内容会丢，而崩溃前最后几行日志恰恰最有用

**为什么日志是这个岗位的核心技能？** 因为技术支持排查问题的唯一手段就是日志。一个不会打日志的人，在现场只能靠猜。

### 3.4 `data_source.h` — 抽象接口（**全项目最重要的一课**）

**问题**：数据可能来自串口、模拟器、MQTT。如果 `DeviceClient` 里写死读串口，那没有硬件时整个项目无法测试。

**解决**：定义接口，`DeviceClient` 只认接口。

```cpp
class IDataSource {
public:
    virtual ~IDataSource() = default;        // ← 这一行绝对不能省
    virtual bool Open(std::string& error) = 0;
    virtual void Close() = 0;
    virtual ReadResult Poll() = 0;
    virtual std::string Name() const = 0;
};
```

**三个必考知识点：**

1. **虚析构函数为什么必须加？**
   通过基类指针 `delete` 派生类对象时，如果基类析构函数不是 virtual，只会调用基类析构函数，派生类的清理代码（关串口句柄）不执行 → 资源泄漏。

2. **`= 0` 是什么意思？**
   纯虚函数，表示"这里只有接口，没有实现，派生类必须自己实现"。含纯虚函数的类是**抽象类**，不能实例化——写 `IDataSource s;` 编译器直接报错。这正是我们想要的约束。

3. **`Poll()` 为什么设计成非阻塞？**
   如果设计成"阻塞直到有数据"，主循环就没机会检查 `Ctrl+C`，程序无法优雅退出。**接口设计要考虑使用场景，不只是功能。**

### 3.5 `mock_source.h` / `mock_source.cpp` — 模拟数据源

**作用**：不需要任何硬件，自己造 JSON 报文。

**要学的东西**：
- **固定随机种子**（`rng_(42)`）：每次运行数据一样，方便复现问题。如果每次数据都不同，你永远说不清"这个问题是不是随机的"
- **故意注入坏数据**（每 7 帧一次）：演示程序如何处理异常
- **时间控制**：记录 `next_due_ms_`，没到时间就返回"无数据"，保持非阻塞

### 3.6 `serial_port_source.h` / `serial_port_source.cpp` — 串口（**面试最值得讲的文件**）

**核心问题：串口是"字节流"，不是"消息流"。**

一次 `ReadFile` 可能只收到半条 JSON（**半包/拆包**），也可能一次收到三条拼在一起（**粘包**）。这是串口编程第一大坑。

**解决方案（行业标准做法）：**

```
① 定义帧边界 —— 本项目用换行符 '\n'
      （真实协议里也可能是固定长度、或带长度字段的头部）

② 所有收到的字节先追加进缓冲区 buffer_

③ 每次从缓冲区里找 '\n'：
     找到了   → 取出它之前的内容作为一整帧，从缓冲区删除
     没找到   → 这帧还没收完，留着等下次

④ 缓冲区设上限（8KB）：一直收不到换行符就丢弃并报警，
   否则异常数据会把内存撑爆
```

这套逻辑的专业名称叫**分帧**。能讲清楚它是很强的加分项。

**其他三个 Windows 串口细节：**

- **端口名必须加 `\\.\` 前缀**：`\\.\COM3` 可以打开任意编号的串口，而 `COM3` 只能打开 COM1~COM9
- **波特率等参数必须和设备端完全一致**：不一致收到的全是乱码（而乱码的典型表现就是"缓冲区一直找不到换行符"）
- **读超时必须设置**：全设 0 会导致 `ReadFile` 永久阻塞，程序无法响应 Ctrl+C

### 3.7 `device_client.h` / `device_client.cpp` — SDK 主入口

**作用**：读一帧 → 解析 → 回调上报 → 统计。

**要学的东西**：

**(1) 依赖注入**
```cpp
DeviceClient(IDataSource& source, TelemetryHandler handler);
```
传引用 `&` 而不是 `new` 一个，明确表达"**我不拥有它，也不负责销毁它**"。这就是为什么接 MQTT 时不用改这个类。

**(2) 禁止拷贝**
```cpp
DeviceClient(const DeviceClient&) = delete;
```
拷贝一个 client 意味着两个对象共享同一个数据源和统计计数——逻辑上是错的。`= delete` 让编译器在**编译期**帮你拦住错误用法。

**(3) 用枚举而不是 bool 表示结果**
```cpp
enum class ProcessResult { Ok, NoData, ParseFailed, SourceError };
```
因为"失败"分很多种：解析错误可以跳过继续，数据源断开需要重连。用 `bool` 会丢失这个信息。

**(4) 坏数据不能让程序退出**
```cpp
catch (const json::ParseError& e) {
    ++stats_.parse_failed;
    LOG_WARN("丢弃一帧坏数据：" << ... << " | 原始内容: " << read.frame);
    return ProcessResult::ParseFailed;   // 继续跑，不退出
}
```
现场环境里偶发坏帧是常态（干扰、拔插、波特率抖动）。**一帧坏数据就让服务挂掉是不可接受的**——这个取舍面试时很值得讲。

**(5) 统计信息 = 运维思维**
```cpp
struct Stats {
    std::uint64_t frames_received, frames_ok, parse_failed, source_errors;
    std::int64_t last_frame_ms;
};
```
客户说"设备老掉线"，你先看统计：`parse_failed` 涨得快 → 串口参数或分帧问题；`frames_received` 不涨 → 链路根本没通。**光说"跑完了"没有价值，说"成功率 87.5%"才能让人判断链路健不健康。**

### 3.8 `examples/device_sim.cpp` — 示例程序

**好的示例程序的三个标准**：短（30~80 行看完）、完整（含错误处理）、有注释（解释"为什么"）。

**要学的东西**：
- **`std::atomic<bool>` 退出标志**：信号可能在任何时刻打断程序，普通 `bool` 读写不是原子的。信号处理函数里**只能做异步信号安全的操作**——不能 `printf`、不能分配内存，只设标志位最稳妥
- **`SetConsoleOutputCP(CP_UTF8)`**：Windows 控制台默认 GBK，不加这句中文日志会乱码
- **主循环为什么用 `while + sleep` 而不是死循环**：给 CPU 留时间 + 有机会检查退出标志

### 3.9 `tools/iot_debug_main.cpp` — 命令行工具

**作用**：`list` / `mock` / `serial` / `parse` 四个子命令。

**要学的东西**：
- **手写 `argc/argv` 解析**：不引第三方库，理解命令行参数的本质
- **`ReadTextFile` 为什么要处理 BOM**：Windows 记事本和 PowerShell 都可能给文件加 UTF-8 BOM（开头三字节 `EF BB BF`），JSON 解析器看到会直接报错，**而人在编辑器里完全看不出来**——这类问题极难排查
- **`--file` 模式为什么必须存在**：命令行传 JSON 会被 shell 吃掉引号（我们在实测中就踩到了：PowerShell 把 `{"device_id":"dev1"}` 变成了 `{device_id:dev1}`）

### 3.10 `tests/test_json.cpp` — 单元测试

**作用**：44 个断言，覆盖正常报文、转义字符、7 种坏 JSON、业务校验边界、序列化往返。

**要学的东西**：
- **手写断言宏**（20 行）：理解测试框架的本质不过是"自动比较 + 统计失败数"
- **返回非 0 表示失败**：这个约定让 CI 能自动判断代码是否合格——这就是"自动化测试"和"手动点一遍"的本质区别
- **浮点数不能用 `==` 比较**：`0.1 + 0.2 != 0.3` 在计算机里是真的，必须用 `NearlyEqual` 判断差值小于 epsilon

## 4. 没有硬件，怎么验证串口代码？

这是你最关心的问题。按投入从低到高：

| 方案 | 做法 | 能验证什么 | 成本 |
|---|---|---|---|
| **① 模拟数据源** | `iot-debug mock` | 整条链路（除串口驱动层） | 0，现在就能做 |
| **② 单元测试注入** | 在测试里用 `MockSource` 注入半包/粘包 | 分帧逻辑的边界情况 | 0，现在就能做 |
| **③ 虚拟串口对** | 装 [com0com](https://sourceforge.net/projects/com0com/)，建 `COM10↔COM11`，程序开一端、串口助手开另一端 | **真实串口驱动 + 分帧全流程** | 免费，但 com0com 最新版是 2017 年的，Win11 可能有签名问题 |
| **④ 真实硬件** | 买一个 USB-TTL 模块（十几块钱）或 ESP8266 | 全部 | 十几到几十元 |
| **⑤ 在线仿真** | [Wokwi](https://wokwi.com/) 浏览器里跑 ESP32，输出串口数据 | 接近真实的设备行为，可截图 | 免费 |

**我的建议顺序**：现在做 ①② → 有条件做 ③ 或 ④（十几块钱的 USB-TTL 是最划算的投入）→ ⑤ 用来做演示截图。

> **面试时的正确说法**："我没有硬件，所以我做了数据源抽象，用模拟器和虚拟串口对完成了闭环验证，分帧逻辑用单元测试覆盖了半包、粘包、超长帧三种边界情况。真实的硬件时序我没有条件验证。"
> —— **主动划清边界，比含糊过去强一百倍。** 技术面试官最怕的不是你没做过，而是你把没做过的事说得像做过。

第一期刻意把 MQTT 排除了，原因是：**你要先有一个能跑的东西，才有信心继续。** 现在你有了。

第二期要做的：

4. 实现自动重连 + 退避
5. 用 MQTTX 手工验证收发

### ⚠️ MQTT 库选型（2026-09-30 实测，直接影响你能不能用 pacman 一键装）

我在 MSYS2 的包索引里逐个查过，结论和"标准答案"不一样：

| 库 | MSYS2 有包吗 | 结论 |
|---|---|---|
| **libmosquitto** | ✅ `mingw-w64-ucrt-x86_64-mosquitto` **存在** | **选它。**`pacman -S` 一条命令装好头文件和库 |
| paho.mqtt.c | ❌ `mingw-w64-ucrt-x86_64-paho-mqtt-c` **404 不存在**（mingw64 环境同样没有） | 只能自己编源码 |
| paho.mqtt.cpp | ❌ 同上 | 同上，且它依赖 paho.mqtt.c，更麻烦 |
| mqtt_cpp | ❌ | 要自己拉 Boost，不建议第一个用 |

**关键坑：paho 官方那个 Windows 预编译包不能用在你这套工具链上。**

[eclipse-paho/paho.mqtt.c](https://github.com/eclipse-paho/paho.mqtt.c) 的 release 页确实提供 Windows 预编译 zip，但**那是用 MSVC 编译的**。把它链接进 MinGW/UCRT64 的程序会出现 ABI 冲突（一堆 `undefined reference`），这正是第 6 节坑清单第 4 条说的"MSVC 与 MinGW 混用"。

> 所以你第二期的路径是：**用 libmosquitto**，别去碰 paho。
> 另一个注意点：**mosquitto 静态链接在 Windows 上有已知问题**（[mosquitto#3035](https://github.com/eclipse-mosquitto/mosquitto/issues/3035)、[msys2#20604](https://github.com/msys2/MINGW-packages/issues/20604)），**用动态链接**，再把 `libmosquitto-1.dll` 复制到 exe 同目录。

## 6. 你会遇到的坑（我实测踩过的都列在这里）

| # | 现象 | 原因 | 解决 |
|---|---|---|---|
| 1 | `fatal error: iotd/json.h: No such file` | 没加 `-I include`（手动编译）或没配 `target_include_directories`（CMake） | 检查头文件搜索路径 |
| 2 | 链接错误 `undefined reference to ...` | 编译命令里漏了某个 `.cpp` | 手动编译时确保 5 个 src 文件都列上了 |
| 3 | 中文输出乱码 | Windows 控制台默认 GBK | 调用 `SetConsoleOutputCP(CP_UTF8)`；源文件保存为 UTF-8 |
| 4 | `parse` 命令传 JSON 报"键必须是字符串" | **PowerShell/cmd 吃掉了双引号** | 用 `--file` 模式（这是我在实测中真实踩到的坑） |
| 5 | 记事本能打开的文件解析失败 | 文件带 UTF-8 BOM | 代码里已处理，或换 VS Code 保存为"UTF-8 无 BOM" |
| 6 | 串口打开失败 `Access denied` | 端口被串口助手/Arduino IDE 占用 | 关掉占用程序；串口同一时刻只能被一个程序打开 |
| 7 | 串口收不到任何数据 | 波特率不一致 / 没共地 / TX-RX 接反 | 确认双方波特率一致；TX 接对方 RX，GND 必须连 |
| 8 | 收到乱码 | 波特率不匹配 | 试 9600 / 115200；乱码的典型表现是"缓冲区一直找不到换行符" |
| 9 | CMake 报 `Compatibility with CMake < 3.5 has been removed` | 抄了老教程里的 `cmake_minimum_required(VERSION 3.5)` | 写 `3.20` |
| 10 | 改代码后 `ninja` 没反应 | CMake 没检测到改动 | 确认保存了文件；必要时删掉 `build/` 重新 configure |
| 11 | 项目放在中文路径下各种诡异报错 | CMake/MSVC 对非 ASCII 路径支持差 | 用纯英文短路径，如 `D:\dev\iotd` |
| 12 | `pacman -S mingw-w64-ucrt-x86_64-xxx` 报"target not found" | 你在 **MINGW64 终端**里执行了 UCRT64 的包名，或者包名写成了 `mingw64` | 确认终端标题是 **MSYS2 UCRT64**；包名里必须是 `ucrt`。2026-03-15 起 MINGW64 已停止接收新包 |
| 13 | 一堆 `undefined reference`，且混着 MSVC / MinGW 的库 | **两套工具链混用了**（同属 UCRT 也不代表二进制能混链接） | **一个项目只用一套工具链。**改用 MSYS2 后把 `build/` 整个删掉重新 configure |

## 7. 这套代码能怎么用在面试里

### 7.1 三个可以讲的"设计决策"

面试官最爱问"你为什么这么做"。这三个问题你有真实答案：

1. **"为什么把数据源抽象成接口？"**
   → 因为我没有硬件。抽象成接口后，我可以用模拟器开发和测试，接 MQTT 时也不用改核心逻辑。**这是被现实约束逼出来的正确设计。**

2. **"遇到坏数据你的程序会怎样？"**
   → 记录、打印原始内容、跳过、继续跑，并且把失败计数暴露在统计里。一帧坏数据让服务挂掉是不可接受的。

3. **"你怎么知道问题出在哪一段？"**
   → 看统计：`frames_received` 不涨说明链路没通；`parse_failed` 涨得快说明是串口参数或分帧问题。**用指标分段定位，而不是猜。**

### 7.2 三个可以展示的东西

1. **日志截图**：里面有一行 `[WARN] 丢弃一帧坏数据：JSON 解析失败（位置 40）... | 原始内容: {...}`
2. **错误定位输出**：`解析失败：位置 69：对象的键必须是字符串` + `^` 指针
3. **测试输出**：`===== 测试结束：通过 44，失败 0 =====`

### 7.3 一句话介绍这个项目

> "我用 C++17 写了一套物联网设备接入 SDK 和调试工具，把数据源抽象成接口，所以串口、模拟器、以后的 MQTT 可以互换。它主要解决现场排障问题：解析失败的帧会原样打印并带字符位置定位，链路健康度用收到的帧数、解析成功数、失败数三个指标分段判断。"

**注意这段话里没有一个字是编的。** 这就是它的价值。
